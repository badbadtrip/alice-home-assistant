# 4. Умный дом: Home Functions

Код: мост `alice/bridge/internal/home/functions.go` (`handle`), сервер `alice/server/src/main.ts` (маршруты), `control.ts` (`resolveLightCommand`), `execution.ts` (`executeFunction`), `devices.ts`, `domains/build.ts`.

## Что происходит на «включи свет на кухне» сейчас

1. Мост: `GET /functions` — весь каталог (JSON всех функций) по HTTP, разбор на ARM.
2. Мост: `POST /resolve` — сервер разбирает фразу своей грамматикой.
3. Для каждого вызова мост: снова `GET /functions` (перепроверка) и `POST /functions`.
4. Сервер на `POST /functions`: `getDevices(true)` — **пересобирает каталог из реестров HA** (`main.ts`, `buildDevices`), затем `executeFunction`.
5. `executeFunction` (`execution.ts`): вызывает сервис и **опрашивает состояние каждые 100 мс до 2 с**, пока не увидит целевое.
6. Мост формирует ответ и отдаёт TTS.

Итого 4 HTTP-запроса, 2 скачивания каталога, пересборка каталога и до 2 с ожидания на одну команду. Если грамматика не поняла — ещё `GET /state` и LLM-планировщик с JSON до 100 КБ.

## Задачи

### 4.1 Один запрос `POST /execute`
- Сервер: новый маршрут принимает `{text, area, voice_only, previous}`, сам делает resolve → проверку доступа колонки → выполнение → ответ `{answer, calls:[{name,status}], clarify}`. Проверки прав остаются на сервере (они там и так обязательны).
- Мост: для `voice_phrase` и точных совпадений — только `/execute`. Каталог нужен мосту лишь для LLM-планировщика; качать его только на этом пути и кэшировать по ETag.
- **Готово, когда:** точная команда — один HTTP-запрос; `exec_ms` по временной шкале (2.1) упал.

### 4.2 Кэш устройств по событиям, не по времени
- `DEVICE_CACHE_MS = 1000` и `getDevices(true)` на каждый вызов. HF уже подписан на `entity/device/area/label/floor_registry_updated` и `config_entry_updated` (видно в журнале). Сбрасывать кэш по этим событиям; на вызове брать готовый.
- Состояния сущностей и так живые через WebSocket (`api.getEntityState`) — пересборка ради них не нужна.

### 4.3 Подтверждение по событию
- Вместо опроса 100 мс — ждать `state_changed` нужной сущности из уже открытого WebSocket (обещание, которое решается событием или таймаутом).
- Отвечать пользователю, как только HA принял вызов (`accepted`), если устройство медленное: «Включаю». Таймаут подтверждения сократить до 1 с; итог (confirmed/не подтвердилось) — в журнал активности.

### 4.4 HA Assist как основной разборщик
- HA умеет русские интенты «включи/выключи/яркость/шторы/температура/какая температура» с комнатами и устройствами (`conversation/process`, агент `conversation.home_assistant`), с контекстом комнаты через `device_id` колонки.
- План: сначала словарь пользователя (точные фразы), затем HA Assist, затем своя грамматика `resolveLightCommand` для того, чего нет в Assist (например «здесь», свои синонимы), затем LLM.
- Разница экспозиции: у нас метки, у Assist — «Предоставить Assist». Вариант: синхронизировать экспозицию Assist из меток (одна правда) или передавать в Assist только сущности с меткой — проверить, возможно ли ограничение через `conversation/process`. Решить замером: точность на 30 типовых фразах дома и задержка.
- **Готово, когда:** ≥ 90 % команд дома без LLM, медиана < 400 мс от финального ASR до ответа.

### 4.5 LLM-планировщик: компактный вход
- Сейчас в модель уходит весь каталог и всё состояние (до 100 КБ). Сократить: только устройства из названной комнаты/типа, функции без длинных схем; состояние — только нужных сущностей. Меньше токенов — быстрее ответ.

### 4.6 Журнал выполнения
- Сервер пишет `Function 'x': status; N ms` — сделать то же в журнале активности моста с разбивкой `resolve_ms`, `call_ms`, `confirm_ms`.
